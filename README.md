# A star Living — ระบบเวอร์ชัน C# (.NET 8)

พอร์ตจากระบบเดิม `astar-living-be` (NestJS) + `astar-living-fe` (Next.js) มาเป็นชุด desktop + API
เพื่อให้ติดตั้งที่เครื่องลูกค้าได้ด้วย installer ตัวเดียว ไม่ต้องลง Docker และอัปเดตเวอร์ชันเองได้

## โครงสร้าง

| โปรเจค | หน้าที่ |
|---|---|
| `src/AstarLiving.Domain` | entity, enum และ **สูตรคิดเงินทั้งหมด** (ไม่พึ่ง EF/ASP.NET) |
| `src/AstarLiving.Shared` | สัญญาที่ client กับ API ใช้ร่วมกัน (ซองตอบกลับ, DTO, การคุมเวอร์ชัน) |
| `src/AstarLiving.Infrastructure` | EF Core map ตาราง `gv_*` ของระบบเดิม |
| `src/AstarLiving.Api` | ASP.NET Core Web API รันเป็น Windows Service |
| `src/AstarLiving.Pdf` | เอกสาร PDF ด้วย QuestPDF + ฟอนต์ THSarabunNew |
| `src/AstarLiving.Client` | โปรแกรมหน้าจอ WPF (ธีม ฟอนต์ไทยฝังในตัว ตัวเรียก API เมนูตามสิทธิ์) |
| `src/AstarLiving.ServerUpdater` | บริการอัปเดตบนเครื่องแม่ และตัวเฝ้าดูว่าบริการหลักยังทำงานอยู่ |

## เตรียมเครื่องพัฒนา

ต้องมี .NET 8 SDK

```bash
dotnet --version
```

ตั้งค่าเชื่อมต่อฐานข้อมูลของนักพัฒนา (เก็บนอก repo ด้วย user-secrets ไม่ commit)

```bash
dotnet user-secrets set "AstarLiving:Database:ConnectionString" "Host=<host>;Port=5432;Database=<db>;Username=<user>;Password=<password>" --project src/AstarLiving.Api
```

## รัน

```bash
dotnet run --project src/AstarLiving.Api
```

จากนั้นเปิด <http://127.0.0.1:8081/api/swagger>

เส้นทางตรวจสอบสถานะ

```bash
curl http://127.0.0.1:8081/api/health/ready
```

## ทดสอบ

```bash
dotnet test
```

- `AstarLiving.Domain.Tests` — สูตรคิดเงิน ปฏิทินไทย ความเข้ากันได้ของ bcrypt และ **การเทียบผลกับระบบเดิม**
- `AstarLiving.Api.Tests` — เส้นทางล็อกอินและการออก token (ใช้ฐานข้อมูลในหน่วยความจำ)
- `AstarLiving.Pdf.Tests` — สร้าง PDF จริงทุกชนิดและตรวจว่าเนื้อหาพอดีครึ่งหน้ากระดาษ
- `AstarLiving.Infrastructure.Tests` — อ่านตาราง `gv_*` จากฐานข้อมูลจริง
  ข้ามอัตโนมัติเมื่อต่อฐานข้อมูลไม่ได้ ตั้ง `ASTARLIVING_TEST_DB` เพื่อระบุ connection string เอง
- `AstarLiving.Client.Tests` — กฎที่อยู่ของไฟล์ (ห้ามเขียนลงโฟลเดอร์ติดตั้ง) การตีความที่อยู่เครื่องแม่ข่าย และการรอเครื่องแม่ข่ายตอนเพิ่งเปิดเครื่อง

ชุดที่ต้องมีฐานข้อมูลจริงจะข้ามอัตโนมัติถ้าต่อไม่ได้ สั่งให้ทำงานได้ด้วย

```bash
ASTARLIVING_TEST_DB="Host=127.0.0.1;Port=54329;Database=astarliving;Username=asliving_app;Password=..." dotnet test
```

### การเทียบผลกับระบบเดิม (golden fixture)

`tests/AstarLiving.Domain.Tests/Fixtures/legacy-invoice-totals.json` เก็บทั้ง input และ output
ที่ได้จากการรัน **ฟังก์ชันของระบบ NestJS เดิมจริง ๆ** บนข้อมูลจริง เทสต์ฝั่ง C# คำนวณซ้ำแล้วเทียบทีละเคส

สร้างไฟล์ใหม่เมื่อข้อมูลอ้างอิงเปลี่ยน

```bash
cd ../astar-living-be
npx ts-node -T -r tsconfig-paths/register tools/golden-export.ts tmp/golden.json
```

แล้วคัดเคสที่ต้องการ (ทุกเคสที่มีหนี้ค้าง + ตัวอย่างเคสธรรมดา) มาเขียนทับไฟล์ fixture

## ข้อควรรู้เมื่อแก้โค้ด

- **ปีในฐานข้อมูลเป็น พ.ศ.** ทั้ง `gv_payments.year` และ `gv_collection_notices.year`
- **วันที่ของเอกสารคือเวลาไทย + 7 ชั่วโมง** (`ThaiCalendar.NowThaiPlus7Hours`) เป็นฐานของเลขรันเอกสาร
  ถ้าเปลี่ยน เลขเอกสารจะไม่ต่อจากของเดิม
- **ค่าเบี้ยปรับคิดคนละฐานระหว่างหน้า preview กับตอนบันทึกจริง** เป็นพฤติกรรมเดิมที่ตั้งใจคงไว้
  ดูคำอธิบายใน `InvoiceCalculator`
- **"ไม่พบข้อมูล" คืน HTTP 200 พร้อม `statusCode: 404` ใน body** ตามระบบเดิม
  ใช้ `ApiResponseFactory.NotFound` ส่วน `AppException.NotFound` ใช้เมื่อระบบเดิมโยน 404 จริง ๆ
- **ห้ามเขียนไฟล์ลงโฟลเดอร์ติดตั้ง** ตัวอัปเดตแทนที่โฟลเดอร์ทั้งก้อนทุกครั้ง
  ข้อมูลที่ต้องอยู่รอดให้เขียนลง `%ProgramData%\AstarLiving` หรือ `%AppData%\AstarLiving`
- **`gv_receipts_revenues` ใช้ `timestamp` ไม่มีโซนเวลา** ต่างจากตารางอื่นที่เป็น `timestamptz`
  มี converter เฉพาะตารางนี้อยู่แล้วใน `RevenueTransactionConfiguration`
- **การตั้งค่า JSON ต้องตรงกันทั้งสองฝั่ง** ใช้ `AstarJson` ที่เดียว ถ้าตั้งแยกกัน
  ฟิลด์จะกลายเป็นค่าว่างเงียบ ๆ โดยไม่มี error ให้เห็น
- **พจนานุกรมธีมของ WPF ที่เป็นพี่น้องกันมองหาคีย์ข้ามกันไม่ได้** ไฟล์ใน `Themes/`
  ทุกไฟล์จึงต้องรวม `Tokens.xaml` เข้ามาเอง ไม่งั้น Setter จะได้ `UnsetValue`
  แล้วไปพังตอนวัดขนาดหน้าจอ ซึ่งไกลจากต้นเหตุมาก
- **โปรเจค WPF ตัด `System.IO` กับ `System.Net.Http` ออกจาก implicit usings**
  (กัน `Path` ชนกับ `System.Windows.Shapes.Path`) ไฟล์ที่ใช้ต้อง `using` เอง
- **`pg_advisory_xact_lock` มีสองแบบเท่านั้น** คือรับ `bigint` ตัวเดียว หรือรับ `integer` สองตัว
  ไม่มีแบบรับ `bigint` สองตัว ถ้าเขียนผิดจะพังทั้งเส้นทางออกเอกสาร มีเทสต์คุมไว้แล้ว
- **ตัวเลือกวันที่ของ WPF ใช้ปฏิทินเกรโกเรียนเสมอ** แม้ตั้งวัฒนธรรมของเธรดเป็นไทย
  ช่องวันที่ทุกที่จึงใช้ `ThaiDatePicker` ของเราเอง ไม่ใช่ `DatePicker` ของ WPF
- **กล่องเลื่อนลงที่จัดรูปแบบเองต้องใช้ `ItemTemplate` ไม่ใช่ `DisplayMemberPath`**
  เพราะอ่านค่าจาก `SelectionBoxItemTemplate` ซึ่ง WPF เติมให้เฉพาะตอนมี `ItemTemplate`
- **เส้นทางที่ไม่ได้ห่อซองต้องเรียกด้วย `ApiClient.GetRawAsync`** ไม่ใช่ `GetAsync`
  (login, logout, refresh-token, handshake, update-policy) ถ้าใช้ผิดจะได้ `null` เงียบ ๆ
- **`-p:Version=` ต้องไหลไปถึง `AssemblyVersion` ด้วย** ดูเงื่อนไขใน `Directory.Build.props`
  ถ้าขาดไป ทุก build จะรายงานตัวเองว่าเป็น 1.0.0 แล้วระบบอัปเดตจะไม่มีวันเห็นเวอร์ชันใหม่
- **โครงการที่เปิด `UseWPF` จะไม่มี `System.Net.Http` ใน implicit usings** ต้องประกาศเอง
  รวมถึงโครงการทดสอบของฝั่งโปรแกรมหน้าจอด้วย
- **`health/ready` ตอบ 503 เมื่อยังไม่พร้อม ซึ่งเป็นคำตอบที่ต้องอ่าน ไม่ใช่ข้อผิดพลาด**
  `ServerReadiness` จึงเรียกผ่าน `ApiClient.Http` ตรง ๆ ไม่ผ่าน `GetRawAsync` ที่จะโยนทิ้ง
- **ห้ามใส่ชื่อเครื่องหรือพอร์ตตายตัวในที่อยู่ที่ส่งให้เครื่องลูก**
  เครื่องแม่ไม่รู้ว่าถูกเรียกด้วยที่อยู่ไหนในเครือข่ายของลูกค้า
  ที่อยู่รูปจึงคืนแบบสัมพัทธ์ (`/api/images/...`) แล้วให้เครื่องลูกเติมเอง
- **`BitmapImage.Freeze()` ใช้กับรูปที่โหลดจากเครือข่ายไม่ได้** เพราะยังดาวน์โหลดไม่เสร็จ
  มันจะโยนข้อผิดพลาดแล้วได้กรอบว่างเปล่าโดยไม่มีอะไรบอกสาเหตุ
- **`BitmapCreateOptions.IgnoreImageCache` ใช้คู่กับ `StreamSource` ไม่ได้**
  WPF จะหาคีย์แคชจาก `UriSource` ที่ไม่มี แล้วโยน "Key cannot be null"
- **ชื่อวงศ์ฟอนต์ต้องเป็น `TH Sarabun New` (มีเว้นวรรค)** ตามชื่อที่อยู่ในไฟล์ ttf
  ถ้าสะกดผิด QuestPDF ไม่แจ้งอะไรเลย แต่ถอยไปใช้ Lato กับ Leelawadee UI
  ซึ่งกว้างกว่ามาก ทุกคอลัมน์จะตัดบรรทัดและเอกสารผิดรูปทั้งใบ
  ตรวจของจริงด้วย `pdffonts เอกสาร.pdf` ไม่ใช่ดูแค่ว่าไฟล์เปิดได้
- **ไฟล์ `.ps1` ที่มีภาษาไทยต้องมี BOM เสมอ** PowerShell 5.1 อ่านไฟล์ที่ไม่มี BOM
  เป็นรหัสอักขระ ANSI แล้วพังตอนแปลโค้ด ซึ่งจะไปพังที่เครื่องลูกค้าตอนติดตั้ง
  ไม่ใช่ตอน build ตรวจได้ด้วย `[Parser]::ParseFile` ก่อนปล่อยเวอร์ชัน
- **ห้ามเรียก `pg_dump` ตรง ๆ จากตัวติดตั้ง** ฐานข้อมูลตั้ง `scram-sha-256` ไว้
  มันจึงรอรหัสผ่านจากหน้าจอที่ไม่มีอยู่ แล้วล้มเหลวเงียบ ๆ
  ต้องผ่าน `Backup-Database.ps1` ที่อ่านรหัสผ่านจาก DPAPI มาใส่ `PGPASSWORD` ให้

### บั๊กที่เจอตอนทดสอบด้วยหน้าจอจริง

เส้นทางที่เทสต์ยูนิตและการติดตั้งใหม่ไม่ได้แตะ ทำให้โผล่ตอนกดใช้งานจริงเท่านั้น

| อาการ | สาเหตุ | สถานะ |
|---|---|---|
| ทุกคำขอที่ต้องล็อกอินพังบนเครื่องที่ติดตั้งจริง | ตัวติดตั้งไม่เคยสร้างกุญแจ JWT โหมดพัฒนามีกุญแจทดสอบจึงไม่เห็นอาการ | แก้แล้ว |
| ออกใบเสร็จ ใบแจ้งหนี้ และรายรับอื่นไม่ได้เลย | `pg_advisory_xact_lock` ถูกเรียกด้วย `bigint` สองตัว ซึ่งไม่มีฟังก์ชันนี้ | แก้แล้ว มีเทสต์คุม |
| หน้าใบเสร็จและกราฟวิธีชำระเงินว่างเปล่า | ข้อมูลตั้งต้นไม่มีใบเสร็จค่าส่วนกลาง | แก้แล้ว |
| หน้าจัดการผู้ใช้งานและบันทึกการทำงานไม่มี API รองรับ | สองโมดูลนี้ยังไม่ได้พอร์ตมาจากระบบเดิม | พอร์ตแล้ว |
| ทุก build รายงานตัวเองว่าเป็น 1.0.0 | `Directory.Build.props` กลบค่าที่สั่งทับจากบรรทัดคำสั่ง | แก้แล้ว |
| ตรวจสอบการอัปเดตแล้วได้ `NullReferenceException` | ใช้ `GetAsync` กับเส้นทางที่ไม่ได้ห่อซอง | แก้แล้ว เพิ่ม `GetRawAsync` |
| เอกสาร PDF หน้าตาผิดไปทั้งใบ ข้อความตัดบรรทัดเกือบทุกช่อง | ชื่อวงศ์ฟอนต์สะกดผิด เลยถอยไปใช้ฟอนต์สำรองที่กว้างกว่า | แก้แล้ว พร้อมเทสต์ตรวจฟอนต์ที่ฝังจริง |
| หน้ารายงานพิมพ์เป็น PDF ไม่ได้ | ระบบเดิมสร้างไฟล์นี้ที่เบราว์เซอร์ด้วย jsPDF ไม่ได้อยู่ในรายการ endpoint ที่ผมเทียบ | เพิ่มแล้ว สร้างที่เครื่องแม่ |
| คอลัมน์รายงานค้างชำระไม่ตรงกับระบบเดิม | ขาดลำดับ รวมเดือนกับปีไว้ช่องเดียว และชื่อหัวคอลัมน์ต่างกัน | แก้ให้ตรงแล้ว |
| ใบรับเงินอื่น ๆ ใช้ชื่อและผังเดียวกับใบเสร็จ | ระบบเดิมแยกสองชนิดนี้ออกจากกัน | แก้แล้ว ชื่อเป็น "ใบรับเงินอื่น ๆ" และตัดบรรทัดเดือนออก |
| "รวมเป็นเงินทั้งสิ้น" ถูกตัดสองบรรทัดในใบเสร็จ | คอลัมน์กว้าง 60 แทนที่จะเป็น 80 ตามของเดิม | แก้แล้ว |
| ใบทวงถามมี 3 คอลัมน์ ของเดิมมี 5 | ขาดวันที่กับเลขที่ใบแจ้งหนี้ และใช้คำว่า "รวมเป็นเงินทั้งสิ้น" แทน "รวมเงินทั้งสิ้น" | แก้แล้ว |
| สรุปค่าใช้จ่ายจัดหน้าคนละแบบกับของเดิม | ของเดิมแยกเป็นสองผัง (ทั้งโครงการ/รายบ้าน) ของผมใช้ผังเดียว | เขียนใหม่ทั้งสองผัง |

## เปิดเครื่องแล้วใช้งานได้ทันที

ไม่มีขั้นตอนที่ต้องกดเองหลังเปิดเครื่อง ทุกอย่างเป็นบริการของ Windows ที่ตั้งเป็น
เริ่มอัตโนมัติ และผูกลำดับกันไว้แล้ว

| บริการ | ชื่อ | เริ่ม | พึ่งพา |
|---|---|---|---|
| ฐานข้อมูล | `astarliving-postgres` | อัตโนมัติ | — |
| บริการหลัก | `AstarLiving API` | อัตโนมัติ | ฐานข้อมูล |
| บริการอัปเดต | `AstarLiving ServerUpdater` | อัตโนมัติ | — (เฝ้าดูบริการหลัก) |

ทั้งสามตัวตั้ง `sc failure ... restart` ไว้ ถ้าตัวไหนล้มระหว่างวัน Windows จะเริ่มให้ใหม่เอง
และ `ServerUpdater` ยังถาม `health/live` ทุก 60 วินาที ถ้าไม่ตอบติดกัน 3 ครั้งจะสั่งเริ่มบริการหลักใหม่

### ช่วงที่เครื่องเพิ่งบูต

บริการใช้เวลาเริ่มราว 20-40 วินาที ซึ่งนานกว่าที่ผู้ใช้กดไอคอนโปรแกรม
ถ้าปล่อยไว้ ผู้ใช้จะเจอ "เชื่อมต่อเครื่องแม่ข่ายไม่ได้" ทั้งที่ไม่มีอะไรเสีย
แล้วต้องมานั่งกดเอง ซึ่งเป็นสิ่งเดียวกับที่ลูกค้าไม่อยากเจอจาก docker

`ServerReadiness` จึงถาม `health/ready` ทุก 2 วินาที นานสุด 3 นาที
ระหว่างนั้นหน้าเข้าสู่ระบบปิดปุ่มไว้พร้อมข้อความบอกสถานะ แล้วเปิดให้เองเมื่อพร้อม
**ผู้ใช้ไม่ต้องกดอะไรซ้ำ**

| สถานะที่อ่านได้ | สิ่งที่ผู้ใช้เห็น |
|---|---|
| ต่อไม่ติด | "กำลังรอเครื่องแม่ข่ายเริ่มทำงาน หากเพิ่งเปิดเครื่องอาจใช้เวลาสักครู่..." |
| ต่อติดแต่ฐานข้อมูลยังไม่ขึ้น | "เครื่องแม่ข่ายกำลังเริ่มทำงาน กรุณารอสักครู่..." |
| กำลังปรับปรุงฐานข้อมูล | "กำลังปรับปรุงฐานข้อมูล กรุณารอสักครู่..." |
| ปรับปรุงฐานข้อมูลไม่สำเร็จ | "ระบบฐานข้อมูลมีปัญหา กรุณาติดต่อผู้ดูแลระบบ" |

สองสถานะแรกรอแล้วหายเอง สองสถานะหลังรอแล้วไม่หาย จึงคืนผลทันทีไม่ต้องรอจนหมดเวลา

ถ้าผู้ใช้กดเข้าสู่ระบบตอนเครื่องแม่ยังไม่ขึ้น ระบบจะรอให้อีก 60 วินาทีแล้วลองเข้าสู่ระบบให้เอง
ไม่ต้องให้ผู้ใช้กรอกรหัสผ่านใหม่

## หน้าสำรองฐานข้อมูล

เห็นได้เฉพาะสิทธิ์ SUPERADMIN กดปุ่มเดียวได้ไฟล์สำรอง ณ ขณะนั้นลงเครื่องตัวเอง
พร้อมแสดงสถานะระบบ (ขนาดฐานข้อมูล จำนวนแถว เวอร์ชัน เวลาสำรองล่าสุด)

### สามเส้นทาง แยก "สั่งสำรอง" ออกจาก "ดาวน์โหลด"

| เส้นทาง | วิธี | ทำอะไร |
|---|---|---|
| `v1/system/backup/status` | GET | สถานะระบบ อ่านอย่างเดียว เรียกซ้ำได้ |
| `v1/system/backup` | POST | รัน pg_dump คืน **บัตรผ่าน** ไม่ใช่ตัวไฟล์ |
| `v1/system/backup/{token}/download` | GET | สตรีมไฟล์กลับไป แล้วลบทิ้ง |

แยกสองขั้นเพราะคำขอเดียวที่ห้ามยิงซ้ำคือการสั่งสำรอง
แยกแล้วปิดการลองใหม่อัตโนมัติเฉพาะเส้นนั้นได้ โดยไม่ต้องรื้อของที่หน้าอื่นใช้ร่วมกัน
และขั้นดาวน์โหลดลองใหม่ได้ปลอดภัยเพราะไม่เปลี่ยนอะไร

### สิ่งที่ตั้งใจออกแบบไว้แบบนี้

- **ดาวน์โหลดด้วยบัตรผ่าน ไม่ใช่ชื่อไฟล์** — เส้นทางดาวน์โหลดไม่รับชื่อไฟล์หรือที่อยู่ใด ๆ
  ชื่อที่ผู้ใช้ส่งมาจึงไม่เคยถูกนำไปต่อกับที่อยู่โฟลเดอร์เลย
  ปิดช่องเดินข้ามโฟลเดอร์**ด้วยการออกแบบ ไม่ใช่ด้วยการตรวจ**
  บัตรใช้ได้ครั้งเดียว อายุ 15 นาที และผูกกับผู้ใช้ที่สั่งสร้าง
- **`FileOptions.DeleteOnClose`** — ไฟล์หายแน่นอนแม้คำขอถูกตัดกลางคันหรือโปรเซสถูกฆ่า
  เชื่อถือได้กว่าการสั่งลบทีหลัง
- **เขียนลง `.part` ก่อนแล้วเปลี่ยนชื่อ** — ไฟล์สำรองที่ขาดครึ่งอันตรายกว่าไม่มีไฟล์
  เพราะผู้ใช้จะเข้าใจผิดว่ามีข้อมูลสำรองอยู่
- **ตัวเรียกแยกที่ไม่ลองใหม่และไม่มีเพดานเวลา** — การลองใหม่กับคำสั่งสำรองแปลว่าสั่ง pg_dump ซ้ำ
  และฐานข้อมูลใหญ่ใช้เวลาเกิน 60 วินาทีได้ คุมด้วยปุ่มยกเลิกของผู้ใช้แทน
- **จดเวลาสำรองล่าสุดไว้** — ไฟล์ถูกลบหลังดาวน์โหลด ถ้าดูจากไฟล์อย่างเดียว
  หน้าจอจะบอกว่า "ยังไม่เคยสำรอง" ทั้งที่เพิ่งสำรองไปเมื่อครู่
- **บันทึกทั้งตอนสั่งและตอนดาวน์โหลด** — จังหวะที่ข้อมูลออกจากเครื่องแม่จริง ๆ
  คือตอนดาวน์โหลด ไม่ใช่ตอนสร้างไฟล์

### หนี้ทางเทคนิคที่ต้องรู้

**ACL ของโฟลเดอร์ `%ProgramData%\AstarLiving\backups`** — โดยปริยาย Windows ให้กลุ่ม `Users`
อ่านได้ แปลว่าคนที่นั่งหน้าเครื่องแม่คัดลอกไฟล์สำรองไปได้โดยไม่ต้องล็อกอินเข้าโปรแกรมเลย
**โค้ดฝั่ง API ปิดรูนี้เองไม่ได้ ต้องแก้ที่ตัวติดตั้ง** ระหว่างที่ยังไม่แก้
ต้องถือว่าเครื่องแม่เป็นเครื่องที่ต้องควบคุมการเข้าถึงทางกายภาพ

`pg_dump -Fc` **ไม่สำรองบัญชีผู้ใช้ฐานข้อมูล** การกู้คืนบนเครื่องใหม่ต้องมีบัญชี
`asliving_app` อยู่ก่อน

## แท็บรายงานสองแท็บที่ดึงจากคนละแหล่ง

"ค้างชำระแจ้งกรรมการ" และ "ค้างชำระแจ้งลูกบ้าน" **ไม่ใช่รายงานค้างชำระธรรมดาที่เปลี่ยนคอลัมน์**
ระบบเดิมดึงสองแท็บนี้จากโมดูลสรุปค่าใช้จ่าย ซึ่งต่างจากเส้นทางรายงานปกติสามข้อ

| | ค้างชำระ (ธรรมดา) | แจ้งกรรมการ / แจ้งลูกบ้าน |
|---|---|---|
| เส้นทาง | `/reports/payments` | `/v1/summary_expenses` |
| งวดที่นับ | `NOT_PAY` อย่างเดียว | `NOT_PAY` **และ** `PARTIAL_PAY` |
| การรวมยอด | ไม่รวม หนึ่งแถวต่อหนึ่งงวด | รวมที่เครื่องแม่ ต่อบ้าน / ต่อปี |

**ตัวเลขของสามแท็บนี้จึงไม่เท่ากันโดยตั้งใจ** ไม่ใช่ความผิดพลาด
งวดที่จ่ายมาบางส่วนจะโผล่ในสองแท็บหลังแต่ไม่โผล่ในแท็บแรก และยอดถูกหารตามสัดส่วนที่ยังค้าง

แท็บแจ้งลูกบ้านบังคับให้เลือกบ้านก่อน เพราะเส้นทางนี้รับรหัสบ้านใน URL
หน้าจอจึงเปลี่ยนช่องกรองจากพิมพ์เองเป็นรายการให้เลือกเฉพาะแท็บนั้น

## ระบบอัปเดตอัตโนมัติ

### หลักการเดียวที่ทำให้ทั้งระบบปลอดภัย

เครื่องลูกดึงอัปเดตจาก **เครื่องแม่ในวงแลนเท่านั้น** ไม่ต้องมีอินเทอร์เน็ตเลย
และเครื่องแม่จะยังไม่วางไฟล์ feed ให้เครื่องลูกเห็น จนกว่าตัวเองจะอัปเดตเสร็จ
และผ่านการตรวจสุขภาพแล้ว เครื่องลูกจึงไม่มีทางอัปเดตแซงเครื่องแม่ได้

### ลำดับที่เกิดขึ้นจริง

1. `ServerUpdater` บนเครื่องแม่ตรวจทุก 6 ชั่วโมง ดาวน์โหลด `manifest.json` แล้ว**ตรวจลายเซ็น**
2. ลายเซ็นไม่ผ่าน = จบทันที ไม่แตะอะไรเลย
3. ผ่านแล้วจึงโหลดไฟล์บริการเบื้องหลัง แล้วตรวจค่าแฮช
4. **สำรองฐานข้อมูลก่อนเสมอ** สำรองไม่สำเร็จคือไม่อัปเดต
5. หยุดบริการ แตกเวอร์ชันใหม่ ชี้ทางลัด `api/current` ไปเวอร์ชันใหม่ เริ่มบริการ
6. รอ `/api/health/ready` ผ่านภายใน 120 วินาที ไม่ผ่าน = ชี้ทางลัดกลับแล้วเริ่มของเดิม
7. ผ่านแล้วจึงมิเรอร์ไฟล์ของโปรแกรมหน้าจอ แล้วเปลี่ยนชื่อ `releases.win.json.staged`
   เป็นชื่อจริง (การเปลี่ยนชื่อเป็น atomic เครื่องลูกจึงไม่มีทางอ่านไฟล์ที่ยังโหลดไม่เสร็จ)

### ฝั่งโปรแกรมหน้าจอ

ปุ่ม **ตรวจสอบการอัปเดต** อยู่มุมขวาล่าง กดแล้วตอบเสมอแม้เป็นเวอร์ชันล่าสุดอยู่แล้ว
และมีการตรวจเงียบ ๆ อัตโนมัติหลังเปิดโปรแกรม 20 วินาที จำกัดไม่เกิน 6 ชั่วโมงต่อครั้ง

ค่าเริ่มต้นคือ **ติดตั้งเมื่อปิดโปรแกรม** เพราะคนที่กำลังออกบิลค้างอยู่
ไม่ควรถูกบังคับปิดโปรแกรมกลางคัน ผู้ใช้เลือกติดตั้งทันทีได้

### การคุมเวอร์ชัน

ทุกคำขอแนบหัว `X-AL-Contract` ถ้าอยู่นอกช่วงที่เครื่องแม่รองรับจะได้ `426 Upgrade Required`
พร้อมข้อความไทยที่บอกชัดว่าต้องอัปเดตฝั่งไหน แล้วโปรแกรมจะขึ้นกล่องบังคับอัปเดตที่ปิดไม่ได้

| สถานการณ์ | สิ่งที่ผู้ใช้เห็น |
|---|---|
| โปรแกรมเก่าเกินไป | "โปรแกรมของคุณเป็นเวอร์ชันเก่า ต้องอัปเดตก่อนใช้งาน" |
| เครื่องแม่เก่ากว่าโปรแกรม | "เครื่องแม่ข่ายยังไม่ได้อัปเดต กรุณาอัปเดตเครื่องแม่ข่ายก่อน" |

เส้นทาง `handshake`, `health` และ `update-policy` ถูกยกเว้นจากการกั้นนี้
ไม่อย่างนั้นโปรแกรมเก่าจะถามไม่ได้ด้วยซ้ำว่าตัวเองเก่าไปแล้ว


ข้อควรระวัง

- **ต้องเรียก `vpk download` ก่อน `vpk pack` เสมอ** สคริปต์ทำให้แล้วเมื่อระบุ `-FeedUrl`
  ถ้าไม่มี จะไม่มีไฟล์ส่วนต่าง ลูกค้าต้องโหลดเต็มก้อนทุกครั้ง (6.4 MB แทน 18 KB)
- **ถ้าไม่เซ็น manifest เครื่องแม่ของลูกค้าจะปฏิเสธชุดนั้น** ซึ่งเป็นพฤติกรรมที่ตั้งใจ
  เครื่องที่ยังไม่ได้ตั้งกุญแจสาธารณะจะปฏิเสธทุกชุด ปลอดภัยกว่าการเปิดรับทุกอย่าง
- **คัดลอก `manifest.json` ขึ้นเซิร์ฟเวอร์เป็นไฟล์สุดท้ายเสมอ**
  เพราะเครื่องแม่เริ่มอัปเดตทันทีที่เห็นไฟล์นี้

### ค่าตั้งใน machine.json

```json
{
  "AstarLiving": {
    "Updater": {
      "FeedUrl": "https://<เซิร์ฟเวอร์>/astarliving",
      "Channel": "stable",
      "ReleasePublicKey": "<กุญแจสาธารณะที่ Pack-Release.ps1 พิมพ์ออกมา>"
    }
  }
}
```

ปล่อย `FeedUrl` ว่างไว้ = ปิดการอัปเดตอัตโนมัติ ซึ่งเหมาะกับไซต์ที่ไม่มีอินเทอร์เน็ต
ตัวเฝ้าดูบริการหลักยังทำงานตามปกติ

## การติดตั้งที่เครื่องลูกค้า

ตัวติดตั้งไฟล์เดียวทำทุกอย่างให้จบในครั้งเดียว ไม่ต้องลง Docker และไม่ต้องตั้งค่าอะไรเพิ่ม

1. ติดตั้งตัวรันโปรแกรม .NET 8 แบบออฟไลน์
2. ติดตั้ง PostgreSQL 16 ที่มากับตัวติดตั้ง (ตัดไฟล์ที่ไม่ใช้ออกเหลือราว 75 MB)
   สร้างคลัสเตอร์ บัญชีผู้ใช้ และฐานข้อมูลให้อัตโนมัติ
3. ลงทะเบียนบริการเบื้องหลังเป็น Windows Service และเปิดพอร์ตใน Firewall
4. ตอนเปิดใช้งานครั้งแรก ระบบสร้างตารางทั้งหมดและใส่ข้อมูลตั้งต้นให้

### บัญชีเริ่มต้น

| ผู้ใช้ | รหัสผ่าน | สิทธิ์ | ใช้ทำอะไร |
|---|---|---|---|
| `admin` | `password123` | SUPERADMIN | จัดการโครงการและผู้ใช้งาน |
| `manager` | `password123` | ADMIN | งานประจำวันทุกหน้าจอ: ออกบิล ใบเสร็จ ใบทวงถาม รายงาน |

**ต้องเปลี่ยนรหัสผ่านทั้งสองบัญชีก่อนส่งมอบให้ลูกค้าใช้งานจริง**

### ข้อมูลตั้งต้นที่ให้มา

โครงการตัวอย่าง 1 โครงการ ลูกบ้าน 10 หลัง (อัตราส่วนกรรมสิทธิ์ต่างกัน)
งวดค่าส่วนกลางย้อนหลัง 5 เดือน รวม 50 งวด สถานะคละกันทั้งชำระแล้วและค้างชำระ
พร้อมใบทวงถาม ค่าเบี้ยปรับ ใบเสร็จค่าส่วนกลาง 25 ใบ (คละทั้งเงินสด โอน และเช็ค)
และใบเสร็จรายรับอื่น ๆ ตัวอย่าง ทุกหน้าจอจึงมีข้อมูลให้ลองใช้ทันที

ข้อมูลตั้งต้นถูกสร้างเฉพาะตอนที่ฐานข้อมูลยังไม่มีผู้ใช้งานเลย
ถ้าชี้ไปที่ฐานข้อมูลเดิมของลูกค้า ระบบจะผูกเข้าระบบ migration โดยไม่แตะข้อมูลใด ๆ

### ประกอบตัวติดตั้ง

```bash
powershell -ExecutionPolicy Bypass -File build/Build-Installer.ps1 -Version 1.0.0
```

ต้องเตรียมไฟล์เหล่านี้ไว้ใน `build/vendor` ก่อน (ไม่ได้เก็บในระบบควบคุมเวอร์ชันเพราะขนาดใหญ่)

| ไฟล์ | ที่มา |
|---|---|
| `postgresql-16.x-windows-x64-binaries.zip` | <https://www.enterprisedb.com/download-postgresql-binaries> |
| `runtime/windowsdesktop-runtime-8.0-win-x64.exe` | <https://dotnet.microsoft.com/download/dotnet/8.0> |
| `runtime/aspnetcore-runtime-8.0-win-x64.exe` | แหล่งเดียวกัน |

ขั้นตอนสุดท้ายใช้ Inno Setup 6 ประกอบเป็นไฟล์ `.exe` ไฟล์เดียว ลงด้วย

```bash
winget install --id JRSoftware.InnoSetup --exact
```

รุ่นใหม่ลงไว้ที่ `%LocalAppData%\Programs\Inno Setup 6` ไม่ใช่ `Program Files`
สคริปต์จึงหาจากทั้งสองที่ให้เอง

ผลลัพธ์คือ `artifacts/AstarLivingSetup-<ver>.exe` ขนาดราว 105 MB
(เทียบกับ Docker Desktop พร้อม image ของระบบเดิมที่ราว 6 GB)

### ที่อยู่ของข้อมูลบนเครื่องลูกค้า

| อะไร | อยู่ที่ไหน |
|---|---|
| ฐานข้อมูล | `%ProgramData%\AstarLiving\pgdata` |
| การตั้งค่าและไฟล์ลับ | `%ProgramData%\AstarLiving\config` |
| ไฟล์สำรอง | `%ProgramData%\AstarLiving\backups` |
| ไฟล์ที่ผู้ใช้อัปโหลด | `%ProgramData%\AstarLiving\uploads` |
| บันทึกการทำงาน | `%ProgramData%\AstarLiving\logs` |

ทั้งหมดอยู่ **นอก** โฟลเดอร์ติดตั้ง เพราะตัวอัปเดตแทนที่โฟลเดอร์ติดตั้งทั้งก้อน
และการถอนการติดตั้งจะไม่ลบโฟลเดอร์นี้ พร้อมสำรองฐานข้อมูลลง
`%ProgramData%\AstarLiving\backups\uninstall-<วันเวลา>.dump` ให้ก่อนเสมอ

ไฟล์สำรองไม่ได้ไปอยู่ใน Documents เพราะตัวถอนการติดตั้งทำงานในชื่อผู้ดูแล
ไฟล์จึงจะไปโผล่ในโปรไฟล์ที่ลูกค้าหาไม่เจอ
